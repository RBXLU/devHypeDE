# Архитектура HypeDE

## Главный принцип: логика отдельно, графика отдельно

Среда рабочего стола устроена так, что почти всё в ней проверяется глазами:
запустил сеанс, покликал, посмотрел. Это медленно и ненадёжно — половину
ошибок так не увидишь.

Поэтому в HypeDE всё, что можно посчитать без экрана, посчитано без экрана:

* куда поедет окно при смене раскладки;
* какое окно получит фокус при `Super+→`;
* какой цвет получит текст на кнопке;
* что произойдёт с окнами, если рабочих столов стало меньше.

Всё это — обычные функции над обычными данными, и на них написаны тесты.
Wayland, OpenGL и GTK подключаются на самом краю, где без них не обойтись.

Отсюда и деление на крейты.

## Крейты и зависимости

```

│    цвет    │◄──┤   настройки   │──►│    протокол    │
└─────┬──────┘   └───────┬───────┘   └───────┬────────┘
      │                  │                   │
      └──────────────────┼───────────────────┘
                         │
      ┌──────────────────┼───────────────────┬────────────────┐
      │                  │                   │                │
┌─────▼──────────┐ ┌─────▼──────┐ ┌──────────▼─────┐ ┌────────▼────────┐
│   composit or  │ │   shell    │ │     files      │ │    settings     │
```

Стрелки идут только вниз: нижние крейты ничего не знают о верхних. Композитор
не может случайно попасть в зависимость от файлового менеджера, а движок
анимаций не знает даже слова «окно».

### hype-anim

Кривые сглаживания (включая кубические Безье, как `cubic-bezier()` в CSS) и
пружинная физика с аналитическим решением для всех трёх режимов затухания.

Главная возможность — **перенацеливание**: анимации можно на ходу назначить
новую цель, и она продолжит движение с текущей скоростью, без рывка. Без этого
перетаскивание окна в плитке выглядит чередой дёрганий.

Пружина задаётся не длительностью, а физикой (жёсткость, затухание, масса), и
длительность вычисляется из неё. Поэтому при замедлении анимаций пружина не
растягивается во времени, а становится мягче — характер движения сохраняется.

### hype-theme

Цвет считается в OKLCH, а не в HSL. Причина простая: в HSL «сделать светлее на
10%» для жёлтого и для синего даёт визуально разный шаг, и палитра выглядит
грязной. OKLab строился так, чтобы равные шаги воспринимались глазом одинаково.

Из одного акцентного цвета строится вся палитра. Каждая пара «текст на фоне»
проверяется на контраст по WCAG, и если акцент выбран неудачно, цвет текста
автоматически сдвигается до читаемого. Испортить читаемость выбором цвета
нельзя — это проверено тестом на восьми разных акцентах в обеих схемах.

Акцент при этом **не приводится к единой светлоте**: иначе жёлтый становился бы
оливковым. Границы нужны только для крайностей — почти чёрная кнопка одинаково
непригодна, каким бы ни был замысел.

Тема выгружается в CSS для GTK-приложений. Одних именованных цветов
libadwaita недостаточно: обычное GTK-приложение о них не знает, поэтому
генерируются и настоящие правила для базовых виджетов.

### hype-config

Один файл `config.toml` на всю среду. Любая пропущенная секция берётся из
значений по умолчанию, поэтому пользователь держит в файле только то, что
действительно менял.

Сочетания клавиш разбираются из строк вида `Super+Shift+Q`. Разбор снисходителен
к регистру и синонимам (`Mod4` = `Super` = `Win`), но **не** к опечаткам в имени
клавиши: `Super+Retrun` — это ошибка конфига, а не тихо мёртвая привязка.

Список действий среды один и тот же для горячих клавиш и для протокола
управления. Это избавляет от двух расходящихся наборов команд.

### hype-ipc

Построчный JSON по сокету в `$XDG_RUNTIME_DIR`. Формат выбран намеренно
скучный: такой поток читается человеком в терминале и разбирается из shell
через `jq`. Пропускная способность здесь не нужна — за кадр проходит десяток
сообщений, а не десяток тысяч.

Форма сообщений закреплена тестом: по ней будут писать скрипты, а значит, она
часть внешнего интерфейса.

В том же крейте живёт `hypectl`.

### hypede-compositor

Разделён надвое.

**Чистая логика** — `layout`, `workspace`, `window_anim`, `roles`. Ни строчки
Wayland, всё под тестами. Здесь живут ответы на вопросы «где будет окно» и
«куда уйдёт фокус».

**Обвязка smithay** — `state`, `handlers`, `input`, `winit`, `ipc`. Здесь
протоколы, отрисовка и ввод.

Раскладка — «главное окно и стопка»: первое окно занимает колонку заданной
доли ширины, остальные делят вторую по вертикали. Зазоры ужимаются, если экрана
не хватает: лучше показать окна без отступов, чем выдать им нулевой размер.

Переход фокуса по направлению берёт ближайшее окно в нужной стороне, штрафуя
смещение поперёк вдвое: окно чуть выше, но рядом, ощущается более «правым», чем
далёкое и ровно напротив.

### hypede-shell, hypede-files, hypede-settings

Приложения на GTK 4. В каждом та же схема: логика отдельно и под тестами,
виджеты отдельно.

## Как всё запускается

```
hypede-comp
  ├─ читает ~/.config/hypede/config.toml
  ├─ выгружает CSS темы в ~/.cache/hypede/theme.css
  ├─ поднимает сокет Wayland (wayland-1)
  ├─ поднимает сокет управления (hypede-wayland-1.sock)
  ├─ запускает панель (hype-shell)
  └─ запускает программы из autostart
```

Приложения среды при старте читают тот же `theme.css`. Если его нет, они просто
берут системную тему: любое из них можно запустить и вне сеанса HypeDE.

## Что пока сделано временным решением

Честный список — чтобы не искать сюрпризы в коде.

1. **Роль окна определяется по `app_id`.** Панель и лаунчер узнаются по
   идентификатору приложения, потому что протокола `wlr-layer-shell` в
   композиторе ещё нет. Правило намеренно узкое: точное совпадение строки,
   чужая программа панелью не притворится.
2. **Анимируется положение окна, но не его размер.** Клиенту сообщается сразу
   конечный размер: пересогласовывать его каждый кадр — значит заставить
   приложение перерисовываться шестьдесят раз в секунду впустую. Плавное
   изменение размера и прозрачность требуют своих элементов отрисовки.
3. **Перетаскивание окон мышью не реализовано.** В плитке оно не нужно, для
   плавающих окон — следующий шаг.
4. **Кадр рисуется постоянно, а не по изменению.** Вложенный бэкенд это
   переживает; для работы от батареи нужна отрисовка по повреждённым областям.
5. **Снимок экрана перекладывается на внешнюю утилиту** до появления протокола
   `wlr-screencopy`.
